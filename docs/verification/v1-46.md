## 行为与权限边界

缺少 Selection revision 时使用不可变的默认 LocalOperatorOnly。启用 PLC 选择须由本机
用户以 ManageRecipeSelectionMap 权限和精确绑定的 Step-Up 发布独立版本化 Policy/Map。
Map 只接受非零选择码及精确 RecipeReference、ReleaseId、ReleaseRecordContentHash；变更时
验证旧、新 Map 的全部受影响 release。相同 Id/Version 不能改写内容。

PLC 使用独立的 Request/ACK/Sequence/Code 输入块及 Response/Outcome/Reason/Sequence/Code
输出块；不得与生产 Trigger、结果交付、心跳、工件身份或结果负载寄存器重叠。
稳定请求身份为 endpoint + controller epoch + dedicated request sequence，跨 Runtime 重启去重。
请求观察先入库并为余下事实保留容量，随后才可运行完整激活管线。首次冲突固定为忙拒绝，
不排队，也不撤销已经持有预留的人类激活、Map 变更或结果交付。

准入会原子清除 Runtime Ready 并解除布防；实际拥有连接的发送栅栏完成 PLC Ready 清除后
才允许候选准备。成功、失败及原配置恢复沿用完整 Recipe Activation 管线。PLC 记录使用
真实 PlcAdapter actor 与专用系统能力，不伪造用户、Session 或 Step-Up。成功事实先入库，
再发布应答；ACK、应答清除及全部请求字段归零分别记录。成功后保持 Disarmed。

安全撤销 Ready 可以先于请求审计完成；审计容量不足不能阻止这个安全动作。
必须等待持久 RequestObserved 和实际 Ready 清除的是候选算法准备、相机配置等激活 I/O。

协议异常同步撤销尚未提交的 capability。最终提交已取得执行权后，迟到异常不会改写
已提交的成功；它仍可要求恢复并保持 Ready=false。启动恢复只补齐旧请求的 Decision/Fault，
不重建激活能力，不重放 PLC 响应，不伪造 ACK 或归零。

Schema 31 为显式可选能力，保留旧 human v1/v2 激活哈希及 49 字段身份负载。
PLC 使用封闭的 v3 激活记录和 50 字段身份负载。启用或移除该存储配置需要显式迁移，
本票不自动修改旧数据库版本。所有查询和写入验证中央审计链与本地事实的双向引用。
