## 实现边界

生产交付的不确定性保留在原 Inspection 下。冷启动先验证持久账本，存在未完成记录时
进入 Recovery，打开恢复通信连接之前必须完成明确的人工授权。历史 Core、报文合同、
固定 payload 和原控制器周期不会因恢复被重新编码或替换；报警确认不能替代 ResultAck。

人工请求绑定 Inspection ID、精确前序事件哈希、原因、实物处置和处置说明。Runtime
要求真实物理交互会话、ManualRecovery 权限与针对完整请求的新鲜 Step-Up。部署需显式
注册唯一匹配的物理停线证据 provider，并冻结来源版本、实际程序集、端点及新鲜度预算。
缺少 provider、非停线、证据陈旧、来源代次变化均拒绝；软件 Ready/Busy 不作为安全证明。

恢复等待整个旧生产任务真实结束，包含观察器、算法、相机、工件身份来源及通信资源。
授权和实物处置的审计先提交，随后仅清理 Runtime 拥有的协议输出，重新验证双向心跳、
控制器同步、Trigger/Ack 低电平稳定窗口。恢复不写 PLC 的 Ack、不补造普通结果，
也不调用自动结果对账。最终完成事实仍需提交，未能确认完成时保留待恢复状态。

一次 Inspection 的恢复会话与每次人工授权尝试分别保留。失败后重试仍需要新的明确
命令、Step-Up 和安全证据；不能通过重入同一物理 transport 执行第二次操作。
全部待恢复 Inspection 清除后回到普通未武装流程，生产门槛和另行 Arm 仍生效。
已接受的物理操作使用 Runtime 自己的期限和关闭信号；UI 取消等待不能撤销已提交授权。
按 ADR-0107，注销或空闲锁定也不会中止已经接受的安全清理；清理继续关联原始授权尝试，
任何新恢复请求仍需重新登录和新的 Step-Up。

存储显式启用 `ProductionStoreOptions.ProductionRecovery` 后使用 schema 30，允许新的
人工恢复命令编号 53，并复用既有生产事件账本和中心审计结构。恢复关闭时保持旧 28/29
数据库定义；旧数据库启用恢复返回 `ProductionRecoveryGovernedMigrationRequired`，
schema 30 关闭恢复返回 `ProductionRecoveryConfigurationRequired`。普通启动不自动迁移。
旧 schema 28/29 保持原有事件哈希、二进制 envelope 和内部存储写入契约；历史恢复标记
可以冷读。schema 30 的恢复必须包含完整的授权记录，并拒绝通用事件写入入口。

维护页面读取待恢复列表，显示原周期、最后持久阶段、不确定性、Core 与报文引用。
读取失败保留可见旧事实并禁用命令；取消、退出或会话变化使旧请求失效。
