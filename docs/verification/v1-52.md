# V1-52：耐久 Outbox 的稳定身份与精确报文交付

关联 GitHub #53，父规格 D08、D10、T13，以及 ADR-0061、0063、0064、0072–0074。
本票实现、完整开发检查、包消费者和审查结果见下方通过记录；这些开发证据不替代正式发行与真实工位资格。

## 配置与交付契约

`ProductionStoreOptions.Outbox` 显式声明完整路由清单、Required／BestEffort、逻辑目的地、
Payload Contract、接收方契约、接收方 ECDSA P-256 公钥、适配器契约及容量、次数、期限。
`AddSharpInspectOutbox` 注册独立连接绑定及对应 transport。未配置路由不会启动外部发送。
逻辑路由和连接配置分别绑定版本与哈希；地址不进入 Core 或 Outbox 报文。
本票提供显式 HTTP POST transport，禁止自动重定向，确认体最多 16 KiB。

部署报警政策按已配置路由类型，为 `Runtime.Outbox` 映射 `OutboxRequiredDeliveryBlocked`（`BlockNewTriggers`）和
`OutboxBestEffortDeliveryFailed`（`None`）；配置存在图片最终化时，仍须保留原图片完整性及积压报警规则。
Required 清单还须与已发布 Trace Storage Policy 及 Deployment Scope 精确匹配。
已有数据库启用本功能需通过下述迁移入口；不能仅更换选项后直接以普通写入器打开旧 schema。

初始 Payload Contract 为 `SharpInspect.Outbox.CoreInspection/1`。
Runtime 在进入提交队列前，将完整 Core、每个 Delivery ID、精确 UTF-8 JSON 字节、
字节长度、内容哈希及路由版本冻结为一个 batch。序列化使用有界内存与原始提交期限，
不在 SQLite 事务或生产锁内执行外部 formatter。重试不读取当前 Recipe，也不重新序列化。
报文只包含冻结核心事实和已冻结结构化结果，不内嵌图像、文件路径或下载地址。

Required 报文无法准备时拒绝 Core 提交。BestEffort 报文超限留下有原因的不可发送义务，
不伪造空报文。Core、Delivery、Created 事件、Pending 投影与中央审计在同一事务提交；
最后的提交围栏拒绝时全部回滚，重试复用原 batch。提交成功前，发送器不可见这些义务。

## 尝试、确认与恢复

工作器不依赖 PLC 或 UI 会话。启动先验证本地完整账本，再分页读取未结束义务。
每条路由同时最多一个物理发送，最多 64 条路由；唤醒队列容量为一，空闲轮询间隔一秒。
每次发送前先持久化 `AttemptStarted`，记录唯一尝试 ID、Runtime epoch、连接绑定和次数。
物理发送与结果发布分离，PLC 可在网络仍等待时发布已耐久的 Core。

只有经过签名、Delivery ID、Payload Hash、路由和目的地验证的 Durable Acceptance，
才能产生内部、单次消费的成功凭据。数据库提交再次核对当前尝试及凭据有效性。
超时、退休或停机后到达的确认不取得成功权限；物理调用仍保留路由槽位，直到实际结束。
五秒退休等待结束不代表线程已终止，也不会启动同一路由第二个物理调用。

Required 连接须提供与部署路由精确匹配的签名幂等能力声明。接收方需原子提交
Delivery ID 去重记录和业务效果，再对外返回耐久确认。同 ID 同哈希重放返回原回执，
同 ID 不同哈希为永久冲突。签名认证接收方身份及声明来源，不证明不诚实接收方的存储实现。
交付语义为有界至少一次，去重业务效果不等于跨系统 exactly-once。

未结束的旧 epoch 尝试在冷启动时追加 `UnknownOutcome`，然后按持久重试预算重发原身份与字节。
失败记录和下一次允许时间使用同一次时钟观察，达到最大退避间隔时也不会因时间差误判超限。
瞬时失败、未知结果和永久失败分别保留；不可用的历史 handler、身份冲突、次数耗尽等不被静默丢弃。
后续 T53 承担人工处置、受控重试和 corrective delivery；本票不补造那些权限或结果。

## 生产门与容量

Required 的永久阻断或积压数量、字节、最旧年龄达到政策上限时，只拒绝新的 Trigger。
未超过上限的瞬时失败和未知结果继续排队，已接受周期继续提交和完成 PLC 握手。
Required 报警映射为 `BlockNewTriggers`；BestEffort 失败映射为 `None`。
两者均由独立 `SharpInspect.Outbox` 系统主体记录，不能冒用当前操作员。
新 Trigger 的最终数据库事务直接检查已验证账本中的 Required 积压，避免运行时投影延迟绕过门。

BestEffort 对生产配置材料的排除只适用于精确匹配部署报警政策的专用规则及其合法生命周期。
普通 `None` 报警、Required 报警、政策变化和异常形态仍然属于材料变化。
报警显示、计数与历史保留完整；排除只用于生产准入材料指纹。

每个已经 Admitted、尚无 Core 的周期，在接受 Trigger 时预留其完整 Outbox 义务。
预留由不可变生产账本推导，不提前创建 Delivery ID 或假待办。每路由预留 delivery、Created、
全部有界尝试／结果，以及报文和后续事实字节；中央审计写入也保留尚未创建 batch 的预算。
Core 事务将预留转为实际记录及剩余尝试预算；无 Core 的故障终止或恢复状态释放未创建部分。
Base64 存储长度参与本地容量计费。报文按路由上限、后续事实按独立的 16 KiB 收据上限预留。
永久失败和报文准备失败释放不会再使用的尝试预留，已写入的失败义务与历史仍保留并计入本地容量。
BestEffort 投递失败本身不关门；权威本地存储无法容纳下一周期的事实时仍拒绝新 Trigger。

## Schema 与历史读取

新功能显式启用 schema 36。签名配置绑定路由数、路由集合、预算，以及旧 Recipe Lifecycle、
Image Evidence、Image Finalization 的存在性和原绑定哈希。没有启用的旧可选功能须同时没有
配置、表和激活证据；已存在的功能保持完整验证。最终化依赖图片证据，图片证据依赖生命周期。
未启用 Outbox 的旧配置继续使用原 schema 与政策指纹。

显式迁移支持 32、33、34、35 到 36，各自保留原可选功能组合。既有 32→33→34→35 路径保留。
28–31 到 36 不在此迁移矩阵内，须拒绝且不改写旧库；不能通过改写 `user_version` 伪装迁移。
迁移日志绑定确切 source／target、旧应用文件哈希及可选功能，恢复不能替换这些绑定。

所有只读 Outbox 页先完整验证中央审计及本地账本，再重建状态、字节和签名回执。
投影篡改、Core 绑定变化、报文变化或审计引用变化均拒绝读取和后续写入。
成功义务不出现在 Pending 页，但不可变交付和尝试历史继续保留。
