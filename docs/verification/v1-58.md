## 授权、负载和生命周期

新增独立 `StartDiagnosticCapture` / `ExportSupportBundle` Permission。
启动、停止和创建包分别绑定完整命令目标、唯一关联 ID、原因及一次性 Step-Up；
开始捕获和停止捕获不能复用认证授权。原因是封闭枚举，不接收自由文本。
既有角色权限集合和默认授权策略哈希保持兼容，新权限必须经受控身份管理显式授予。
单次身份写事务先验证完整签名审计链，再写授权、Accepted 命令和诊断操作准入事实。
UI 的 Accepted 只表示耐久接纳，不能显示为 Active / Completed。

捕获 Profile 防御复制组件集合，绑定部署日志策略、Debug / Trace、持续时间和事件数。
单调时钟和原子计数取最早终点；匹配组件的尝试在分类、配额和队列准入前计数，
非法／秘密字段及已结束算法作用域的迟到尝试也不能规避次数上限。
组件计数不扩大字段许可，producer 配额、sink 容量和速率不会重置或增加。
第 N 次合法尝试可进入队列，随后立即恢复基线；物理生产者、队列和 sink 引用全部退出前
操作仍占用 Busy。取消、锁屏、会话／权限／凭据变化、审计故障、sink 故障和关闭均撤销能力。

本实现没有宣称新负载已经通过精确性能资格。Ready / Armed、执行中、待自动或手动 Arm、
资格操作和独占维护均拒绝诊断支持准入；活动诊断操作也阻止生产准入。
运行时已完成的包仍绑定原授权，取包期间发生本地停止、失效、取消或过期会拒绝返回字节。
取消不能代替实际 I/O 返回。物理工作未退出时保持占用，关闭退场超时记故障并明确失败。

## 支持包与保留权限

必须显式配置 `DiagnosticSupportStoreOptions`、日志策略、Trace Storage Policy 和专用
`SupportBundleOptions`，并验证绑定哈希、同卷本地目录、私有 ACL、文件句柄身份及根目录隔离。
默认 SampleHost 不隐式启用。WPF 只提供配置内组件、等级、数量、时限、原因及 UTC 窗口，
没有任意路径、原始文件、protected detail 开关或任意文件复制动作。

`SupportBundleScope` 要求当前 RuntimeEpoch 和 UTC 起止窗口，可进一步按类型化执行、命令和
捕获 ID 缩小范围；非空身份集合分别与时间／Epoch 条件取交集。公开 API 限制合计 64 个身份，
实际窗口、源记录、源字节和成品字节继续受部署策略约束。
固定投影工厂只读取 safe 诊断历史并重新按当前事件 schema 分类和脱敏。
图片、配方、数据库、原始工件码、凭据、秘密及 protected 字段都不进入默认包。
本票不提供未脱敏 protected 导出能力，支持材料不能当作备份。

包包含精确范围、策略身份、容量、创建／到期时间、排除来源、成员 SHA-256 和整体 SHA-256。
源历史采用有界 newest-tail 扫描，清单明确记录 `exhaustive=false` 和
`earlierHistoryCoverage=Unknown`，不会把有限观察标成完整历史。
固定私有 `.sib` 文件写入、flush、实际回读哈希后，才能写 Sealed 和 Completed 审计事实。
只有当前进程内仍有效的已完成授权可以通过 `ISupportBundleReader` 取得字节。
重启不恢复交付能力。

文件名中的时间和自述哈希不是删除授权。清理只能使用同一读事务中完整签名验证得到的原始
审计 seal，逐项核对文件身份、哈希、字节数和固定到期时间后删除确已过期文件。
无 seal 的残留文件继续占容量，伪造较早文件名或修改内容不能提前释放空间。

## schema 40 与审计闭环

新增不可变诊断配置／事实表，配置激活和每个事实均进入中央签名链。
schema 39 → 40 的受控迁移保留旧行并记录精确目标配置；未配置能力仍使用旧 schema，
旧 reader 拒绝 schema 40。schema 40 继续验证原有 Outbox Recovery、Reconciliation 和 Retention。

每项操作准入保留完整四事实预算，允许 Admitted → Sealed → Completed，
失败／中断可从尚未完成状态终止。Completed 必须已有 Sealed。
捕获记录实际观察事件数；重启无法恢复的观察数量保持 null。
显式停止命令及授权引用，即使在停止续体执行前失效或重启，也从实际已签名事实绑定进终态。
已封存包后发生中断会保留原始 seal 元数据，不能清除它来规避保留规则。
读取状态、seal 和 terminal 写入均在自己的 SQLite 事务内重新验证完整签名链。
