## 行为与权威边界

Runtime 使用固定的 24 个准入门检查部署与版本政策、Active Recipe、已准备算法、资产、相机绑定与配置及健康、PLC 通信与同步、恢复、独占工作、报警、存储完整性与容量、证据对账、积压、身份恢复方式、分层资格和生产周期。每次报告完整列出全部门；未接入的必需能力明确拒绝，不从其他健康状态推断为通过。

34 类实质配置绑定构成目标指纹：工位与安装身份、目标硬件与存储、操作系统与电源配置、.NET、框架候选与构建、Provider 与厂商 Runtime、相机与配置、PLC 端点与政策、Released Recipe、算法与模型、图像规格、存储与证据／日志／诊断／报警／身份／备份／部署／启动政策、性能契约、Conformance Profile、UI 负载、标定、Part Identity 和 PLC Result Contract。缺少某项不能自动解释为不适用。Qualification Context、运行时间与审批身份不进入目标配置指纹，但资格证明须分别精确匹配当前冻结的 Profile、Scope 和 Context。

固定验证器核验 ECDSA P-256 签名及发行者分层授权，区分 Framework、Provider contract、Provider hardware、Performance、Station Acceptance 和适用的 Power-Loss 记录。工位验收必须引用当前有效的各层记录哈希。较新的时间、有效签名或审批不能替代目标匹配、必需检查通过及准确引用。`Fail`、`NotRun`、`Blocked`、`InvalidHarness`、缺失检查和被改成可选的必需检查均不能通过。

Power-Loss 的“不适用”也需要当前受信签名证明：`PowerLoss.claim` 与冻结的可选要求、排除证据哈希、Profile、Scope、Context 和目标精确匹配。裸布尔值或任意排除哈希没有授权力。

公共报告是不可变投影，没有可由宿主设置的通过标志。`CanArm` 由完整固定门集合派生；Runtime 不接受外部报告作为授权输入。Snapshot 与命令 outcome 的新增报告属性保留旧构造函数 ABI。WPF 仅在报告与新鲜 Snapshot 的 epoch/revision 精确相同才显示当前结论。

schema22 账本记录准入授权与报告。`Completed` / `ProductionAdmissionFinalized` 仅表示该授权报告已持久化；不宣称工位曾经进入 Armed。Runtime 在该提交及审计验证完成后，再按当前 epoch、实质状态代次与停止状态检查是否发布 Ready；期间变化则保持 Disarmed。所有会改变选中 ledger heads 或身份权限／凭据／恢复权威的 writer 事务，都在真实 SQLite COMMIT 前通过同一内部观察器同步递增 Runtime 代次并 Disarm；只有 COMMIT 成功才前移观察器基线。该观察器只绑定拥有写租约的唯一 writer handle，读连接不触发。普通身份审计、命令与准入自身账本不会使实质 heads 变化。Finalized 事务也精确复核 heads，变化时持久 Failed/ProductionAdmissionChanged。命令 `Accepted` 沿用接纳请求的语义，实时状态以当前 Snapshot 为准。
