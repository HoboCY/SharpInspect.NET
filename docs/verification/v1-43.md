## 实现边界

Recipe 的 Required／Optional／None 要求保持独立于控制器周期和 Inspection ID。
Required／Optional 使用部署中恰好一个逻辑角色匹配的公开 `IPartIdentityProvider`，
激活检查格式、能力、来源合同和实际 provider 程序集。绑定和静态能力进入部署资格目标；
当前 Ready、来源 epoch/generation 单独参与运行许可。当前来源变化撤销 Arm，
无关来源变化不撤销当前工位许可，普通扫码值更新不视为部署变化。

None 不读取来源，保留旧 Admission/Core 和无身份 PLC Profile 的 v1 哈希路径。
Required／Optional 每次请求最多调用一次锁存，且不等待人工、不竞速、不回退。
Runtime 独立验证 provider 返回的周期关联、来源代次、格式和单调时钟新鲜度，
在获得 command gate 后、分配 Inspection ID 前再次检查新鲜度及当前许可。
Required 缺失、陈旧、歧义或非法时不分配检测身份、不建 Run；Optional 的真实 Missing
生成 NotProvided 证据。成功锁存后即使 Stop／超时撤销准入，也不退回消费令牌。
迟到的 provider 实际任务保留到真实退休，不能重新进入分配检测身份的路径。

PLC 来源通过原通信 owner 执行控制块／版本前读／完整身份块／版本后读／控制块复读，
要求同一非零偶数 revision、同一控制器周期和相同控制字段。UTF-8、长度、填充和状态
均验证，完整原始读取证明进入哈希；公开 PLC provider 只消费这份稳定证明，不再开连接读取。
扫码来源按 Runtime epoch、端点、连接代次和控制器周期关联唯一 stage token，
来源重启清空候选并变更来源代次。重复业务字符串允许，重复 PLC revision 或 stage token
由单一 SQLite writer 在接受事务内拒绝，不以业务字符串作唯一键。

接受后的证据冻结在 Admission 内并使用 v2 编解码，Core 的 PartIdentity 从其派生。
之后扫描、UI 或 PLC 变化不改写原始证据或 PLC payload。schema29 提供独立的签名拒绝／更正账本；
拒绝事实不需要交互身份，也不包含 Inspection ID。异常退出先退休观察器并输出 fault，
再有界写入已观察到的拒绝事实，避免逐条审计等待延迟 PLC fault 输出。
历史更正通过 Runtime 权限、Step-Up 和真实会话校验，以原 Admission 和上次更正引用追加，
命令及授权审计与更正记录在同一事务中提交。
连续更正沿前序更正哈希形成链，原值来自原始证据或上一条更正的新值；更正事件使用当前
Runtime epoch，原始周期的 epoch 留在证据中。陈旧前序和原值冲突在写入事实前转换为普通
持久拒绝，不消费 Step-Up、不追加更正、不把业务冲突升级成审计故障。

激活提交使用最后一次部署观察的 provider revision，在 writer 的最终同步回调内核对；
捕获后来源重启会拒绝激活，锁内不执行 provider 回调。独立拒绝 writer 在同一事务内先
完整验证中央签名链与本账本再追加。schema29 的全部 SQL 投影与命令／授权／原始 Core
引用均参与验证；仅启用身份及新账本时，身份和恢复读取仍使用完整审计范围。
